Decoding iPhone HEIC photos in Chrome: libheif as WebAssembly, loaded on demand and kept out of the bundle

Tanggal: 2026-11-03

I'm the developer of MakeQuickWork, a small set of free browser tools. This post is about its HEIC to JPG converter and the two or three things that took longer than the conversion itself.

iPhones save photos as HEIC by default. Copy a few of them to a Windows laptop, or try to attach one to a form that only takes .jpg, and you find out how unevenly that format is supported. I wanted a converter that runs in the tab, so the photos are never uploaded: https://makequickwork.com/image/heic-to-jpg/

The interesting part is that the browser you're in decides how much work there is.

Safari can decode HEIC itself. Chrome, Edge and Firefox can't, which covers most Windows and Android users, i.e. most of the people who actually have the problem. So the decoder tries the native path first and falls back to libheif compiled to WebAssembly:

Both paths end on a canvas. From there it's canvas.toBlob() as JPG (quality Maximum, High or Medium) or PNG. Rotation is applied on both paths, so photos come out the right way up.

format doesn't come from the file extension or the MIME type. Windows often reports HEIC files with an empty MIME type, so the file input accepts .heic,.heif by extension, and the code then reads the ftyp box and checks the brands (heic, heix, mif1 and friends). A JPG renamed to .heic gets a clear "this is not a HEIC photo" message instead of a decoder crash.

libheif is LGPL-3.0. I'm not a lawyer, but the spirit of the LGPL is that users should be able to swap the library for their own build. If I let the bundler inline it into a hashed chunk, that's hard to do in any practical sense.

So it's not bundled. A build script copies the unmodified libheif.js and libheif.wasm from libheif-js 1.23.5 to /vendor/libheif/, next to the licence text and a SOURCE.txt that points to the corresponding source and says you may replace the two files.
