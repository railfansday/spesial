Part 5: Mirror With Intent: Building Right-to-Left Ready Screens in Jetpack Compose

Tanggal: 2026-11-03

Posted on Nov 3 • Originally published at Medium

Previously: Parts 1 to 4 made screens readable, operable, testable, and alive for assistive technology. This final part is about a different kind of inclusion: the hundreds of millions of people who read Arabic, Hebrew, Persian, or Urdu, right to left.

TL;DR Compose mirrors most layouts for free, as long as you say start and end*, never* left and right*.* The rest of RTL support is judgement. Directional icons must flip; play buttons, checkmarks, and clocks must not. Phone numbers and English product names inside Arabic sentences need isolating. Raw gesture math, slide animations, and custom Canvas drawing don't mirror on their own. Test all of it in minutes with a forced-RTL preview and the ar-XB pseudolocale, then lock the result in with a layout assertion and reviewed LTR/RTL screenshot baselines.

An Arabic launch goes out. The layouts mirror nicely: titles sit on the right, lists align to the right, and the navigation icon moves to the top-right corner. Then a reviewer posts a screenshot. The back arrow, now on the right edge, still points left, deeper into the screen, which in an RTL layout means forward.

It’s a small bug that tells every RTL user the app was never designed with them in mind. It also confuses screen reader users: TalkBack says “Navigate up” about an arrow that visually points forward. The fix is one word:

The AutoMirrored icon set has existed since material-icons 1.6, and the old directional icons are deprecated in favour of it. If your build shows deprecation warnings for Icons.Filled.ArrowBack, that's your RTL backlog announcing itself.

Layout direction is part of the composition, exposed as LocalLayoutDirection. Compose derives it from the device configuration: an Arabic or Hebrew locale means LayoutDirection.Rtl. Every direction-aware API reads it, so start resolves to the left edge in English and to the right edge in Arabic, with no code on your part.

There’s one switch upstream of all of this. Your manifest must opt in:

Without it, the configuration reports left-to-right for every locale, and nothing in this post applies. New projects set it by default. Older apps, and some white-label templates, quietly don’t.

The rule that follows is simple: use the start/end API, and treat every left/right API as a decision you need to justify.

Two details catch even experienced teams:

An icon should mirror when it shows direction through the reading flow: back, forward, next, previous, send, list indentation, or a chevron that opens something “after” the current item. An icon should not mirror when its direction comes from the physical world or a universal convention.

The common failure is the reverse of the opening bug. A well-meaning bulk change adds autoMirrored="true" to every drawable, and suddenly the play button in your Arabic build points backwards. Review mirroring per icon, not per folder.

Arabic sentences regularly contain English: product names, usernames, brand names. Unicode’s bidirectional algorithm usually places them correctly. It goes wrong at the edges, when an inserted LTR fragment starts or ends with numbers or punctuation. Then the surrounding RTL text can grab those characters and reorder them. The fix is to isolate the inserted value so it’s laid out as one unit:

Wrap every runtime value you insert into a translated string: names, titles, search queries. The cost is negligible, and it removes an entire class of bug reports that are almost impossible to reproduce if you don’t read the language.

Digits always read left to right, even inside RTL text. What breaks is sequences with separators. A phone number like +91 98765 43210, placed in an RTL paragraph, can be displayed with its groups in reverse order. To a reader it's a different number entirely. The same applies to ranges ("10–20"), IBANs, card numbers, and version strings.

This is where layouts that mirror perfectly still feel wrong. Anything built on direction-aware APIs is handled for you. Anything built on raw coordinates is not.

Handled for you: HorizontalPager, LazyRow, horizontalScroll, SwipeToDismissBox (its values are StartToEnd and EndToStart), and AnimatedContent transitions built with SlideDirection.Start and SlideDirection.End.

The rememberUpdatedState calls are there for a reason too. pointerInput is keyed only on direction, so without them the gesture would keep calling whichever lambdas existed on first composition. And per Part 2: any swipe-only interaction also needs a custom accessibility action, such as "Next photo," because swipes aren't available to everyone.

Mirror shapes this way, never text. A drawText call inside a mirrored scale block renders backwards, letters and all. Draw labels outside the mirrored block, at positions you calculate from layoutDirection.

You don’t need to read Arabic to catch 90% of RTL bugs. You need five habits, from fastest to most thorough:

1. Previews in both directions. One extra annotation per component:

2. Pseudolocales. Enable them for debug builds:

Then make AR (XB) the active language in your device’s language settings. It renders your English strings right to left, with the characters reversed, so you can review RTL layouts without any translations. Its sibling, en-XA, adds accents and expands text length to expose clipping, and it flags hard-coded strings that never went through resources.

3. Force RTL on a device. In Developer options, enable Force RTL layout direction. It mirrors every app without changing the language, which makes it handy for checking third-party SDK screens your previews never see.

4. A layout assertion in CI. Part 3’s tooling extends naturally:

This test proves placement, not orientation. The opening bug would pass it: the icon reaches the right edge while the arrow keeps pointing left. Bounds can’t see the pixels inside an icon, so pair this with the next habit.

5. *Reviewed LTR/RTL screenshot baselines.* Keep one small fixture holding an icon that must mirror and one that must not, and record it in both directions.

Note: Paparazzi and Roborazzi don’t read the @Preview annotations, so with those tools set the locale or layout direction in the test configuration. Compose Preview Screenshot Testing does use them.

Expected result: the arrow points left in LTR and right in RTL, while the play triangle points right in both. A missing flip shows up as a wrong arrow, and an overbroad mirroring change (the bulk autoMirrored="true" mistake) shows up as a backwards play button. Because both icons sit in one fixture, anyone updating a shared component can see the intended difference at a glance. Record with Paparazzi, Roborazzi, or Compose Preview Screenshot Testing, whichever you already use.

Baselines only help if diffs are reviewed. Check the first recording by eye, ideally with someone who reads an RTL language, and treat “update snapshots” commits with suspicion.
