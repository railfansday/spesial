Building a gemini server in python

Tanggal: 2026-11-03

7 years after its invention, I discovered the Gemini protocol. It’s a kind of “back to first principals” alternative to the web, aimed at providing value to independent content creators away from the noise, bots and trackers of the main web.

In Gemini, a website is called a capsule, the web is called the geminispace. The standard document format is kind of stripped down markdown format called gemtext (Gemini’s HTML equivalent). To surf the geminispace, you need a Gemini client (equivalent of a web browser). After trying a few options such as deedum, I found the Lagrange client, an amazing piece of software written by Jaakko Keränen @skyjake who works for Nokia. The client works on all platforms (mobile and desktop) and is a real pleasure to use.

There are no big corporations on Gemini. Lagrange comes with a bookmark to a “Getting started” page which lists some search engines like keneddy which I understand runs entirely on one guy’s mac mini including the crawler.

After exploring the geminispace a little, I wanted to have a go at implementing my own server. It may not be the ideal language to implement a server, but I’m doing an increasing amount of python development so it seemed like a fun project to use it on. The rest of this post follows a similar step by step process that I went through to implement a Gemini server in python trying to use minimal external dependencies.

So far, we are sending unencrypted data over our socket (similar to plain HTTP requests). Gemini mandates the use of TLS, so for a Gemini client to understand our request we need to encrypt the data with a TLS certificate.

Unlike on the web, which pretty much mandates that server certificates be issued by a specific set of certificate authorities (CAs), it is quite common in Gemini to use self signed certificates. Gemini operates a “Trust on first use” (TOFU) policy for TLS. This works similar to SSH connections where the first time you connect to a host, your client associates it’s certificate with that host. If the certificate changes for subsequent requests, you will get a TLS error (or warning at least) that the server’s identity has changed.

Success 🎉, you should now have a server that a real Gemini client will understand. You should be able to point lagrange (or any other Gemini client) at gemini://localhost/hello and get a page with a Hello heading returned.

What we’ve done so far in enough to serve static pages, however there will come a time where you’ll want to accept user input. To indicate that input is required, the server needs to return status 10 which tells the client to prompt the user for input.

This is a lot more basic than what you’re probably used to with HTML forms and HTTP post. You get a single prompt which is then sent to the same URI as the entire query string once the user fills it in. You cannot send multiple query parameters or provide different input types, the user gets a text box with a single field, that’s it.

We can now accept user input from the user, but how do we know which user it came from? In HTTP world there are many ways to do this, basic auth, oauth2 are common but another way is mutual TLS (mTLS). In this scenario, both the server and client present there own TLS certificates. The server can then identify the client based on its certificate.

mTLS is quite commonly used in enterprise applications for machine to machine communication, but not very common for end user applications due to to the fact that generating, maintaining and instructing the browser to use a client TLS certificate is quite complicated and cumbersome for the average user. Certificates expire, the server needs to agree to trust them, etc.

Unlike with HTTP, where TLS was bolted on later with HTTPS, TLS is native to the Gemini protocol. There is a special set of status codes (6X) around client certificates. If a server sends status code 60, it means that the client must provide a client certificate to access this page. As a result, creating and managing client certificates is encouraged to be supported by Gemini clients (the browsers). Lagrange handles this very well. When a server responds with status 60, the user gets prompted to either use a certificate they created previously, or to create a new certificate with a friendly interface that hides away the complexities of TLS. Once the certificate is created, the page can reload, this time using mTLS with the client supplying the newly created certificate.

Gemini uses TLS in a more simplified way to HTTPS which is not without security trade offs and criticism, but does provide much improved security over unencrypted connections. TLS is used as an asymmetric (public/private key) encryption protocol it is common place in Gemini

These 2 points are where things get difficult with the standard library SSL python module.

The problem is (as far as I could tell) that the ssl module requires the server to be configured to trust the client’s certificate authority upfront before it serves the request. In enterprise / corporate networks this is generally OK as there would likely be conversations upfront to configure the certificate before it was used. This is not practical for a public website (or capsule). With the python ssl module, a certificate generated by an unknown CA will be rejected before we can trust it. This is what led me to use the pyOpenSSL library.

The key difference is that it allows you to configure ssl to accept client certificates and override the certificate verification to supply your own implementation via the set_verify method. By always returning True we can move certificate verification and reading logic up into the Gemini protocol specific code.

What we’ve built so far is a single threaded synchronous server. This means that the server handles one request at a time and cannot accept new connections until the previous request has been dealt with. This works fine when testing on your machine, but will struggle once you have multiple users and your routes are handling more complicated logic and interacting with other systems like databases or third party services. There are several ways to deal with this problem.

The first 2 are parallelism solutions, the second is a concurrency solution. This article explains the subtleties between the 2 better than I can I strongly recommend it. As the article states, concurrency is probably the better choice for I/O bound applications like servers.

In python async/await is handled by the asyncio module. Amongst many other things, asyncio provides a function to start a TCP server using async connection handling. This will replace what we used the socket module for at the very start of this post. Coming from the JavaScript world where everything is async by default it may be a little frustrating that in order to use async await, you may need to rewrite or wrap your code. Going into this in detail perhaps deserves another post but in short pyOpenSSL doesn’t natively support async await so it was necessary to create some wrapper code to interact with it in a non blocking way.

After doing all of this we now have a working Gemini server. The next thing to do is to share it with the world! I wanted to stick to Gemini’s do it yourself kind of ethos and self host this. I found an old Raspberry Pi Model 3 B lying around. This model is from 2016 and has 1GB of RAM. I purchased a memory card and flashed Raspberry Pi OS lite onto it using the raspberry pi imager tool.

I had trouble getting wifi working on the pi, I think it’s something to do with 5GHz not being supported on this model but in the end I thought that a server is probably better wired so I plugged it into my router via ethernet.

Initially I thought of deploying using a docker image but I didn’t really want to rely on docker so I went with a simple systemd service that I deployed using scp and ssh.

I then did something that I haven’t done before, expose a port publicly on my router. I think I did this fairly safely, from the router user interface, I made a firewall rule for TCP port 1965 and routed traffic to that port to the pi and gave it a static IP. There we go I had joined the Geminispace!

What I made was a basic TODO application. I’m not sure it has much practical usage with all the fully featured todo list applications available, but it was a fun to make. You can visit it in a gemini client by going to gemini://todo.willmunn.xyz. The source code is available on codeberg.
