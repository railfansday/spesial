Your AI-built Next.js 16 landing page looks fine. Its link preview might not: 6 metadata traps and the prompts that fix them

Tanggal: 2026-11-03

An AI-built Next.js 16 landing page can look perfect in your browser while its link previews, robots.txt, and sitemap still point at localhost:3000, lose their image on every subpage, or show up as a blank card. Here are six metadata traps, each checked on a real build, with a fix and a prompt you can paste into Cursor, Claude Code, or ChatGPT.

The examples come from a waitlist landing page built prompt by prompt on create-next-app 16.4 (Next.js 16.4, React 19.3, Tailwind v4). None of these show up when you click around on localhost, which is why they slip through. You only notice when someone shares the link.

VERCEL_ENV is a Vercel system variable that's available at build time, so local builds and preview deploys are left alone. In our test, faking VERCEL_ENV=production with an empty URL or a localhost URL failed the build. A real domain passed.

In next.config.ts, fail the build when VERCEL_ENV is "production" and NEXT_PUBLIC_SITE_URL is empty or contains localhost. Keep the localhost fallback in lib/site.ts for dev. Add NEXT_PUBLIC_SITE_URL to .env.example with a comment saying it must be set in Vercel's Production environment.

The natural reaction is to add the variable in the Vercel dashboard and refresh. That doesn't work, for two reasons.

First, NEXT_PUBLIC_ variables are inlined when you run next build. The Next.js docs say they're "frozen with the value evaluated at build time." We built with https://a.example and started the server with https://b.example. The page and robots.txt both still said a.example.

Second, a lot of your SEO output is static. In our test runs, npm run build marked the OG image, robots.txt, sitemap.xml, and the icon as static routes. The docs call robots.js and sitemap.js special Route Handlers that are "cached by default." When we built without the variable and only set it at next start, the dynamic home page picked it up, but robots.txt, the sitemap, and the static admin page stayed on localhost.

Vercel's docs are explicit too: environment variable changes "only apply to new deployments. You must redeploy." And a variable you add only for Preview won't exist in Production.

If you'd rather not maintain a variable at all, Vercel sets VERCEL_PROJECT_PRODUCTION_URL on every deployment, previews included, and its docs suggest it for OG image URLs. It has no https://, and since it doesn't start with NEXT_PUBLIC_ it won't reach client components, so only use it in server code.

After changing any NEXT_PUBLIC_ variable or anything used by robots.ts, sitemap.ts, or opengraph-image.tsx, tell me to redeploy, not just refresh. Add a line about this to the README's deploy notes.

Next.js merges metadata shallowly, so a page that defines openGraph replaces the parent's whole openGraph object. On our build, that page lost og:url, og:site_name, og:type, og:image, and twitter:image. The root opengraph-image.tsx still existed, but the page no longer pointed at it. Share that link and you get a card with no image.

The docs suggest pulling the shared fields into a variable and spreading it. Include the image, or you'll get everything back except the part people actually see:

With that, the page had og:image and twitter:image again. The opposite case is quieter. A page that defines no openGraph inherits everything, including the layout's og:url. Our status page announced the homepage as its URL.

Create lib/seo.ts exporting sharedOpenGraph (siteName, type, and the OG image as /opengraph-image, 1200×630). Every page that sets openGraph must spread it first and set its own title and url. Never set a partial openGraph object on a page.

opengraph-image.tsx with ImageResponse looks like normal JSX, so assistants write it like a normal component. It isn't one. The docs say: "Only flexbox and a subset of CSS properties are supported. Advanced layouts (e.g. display: grid) will not work." There's also a 500 KB bundle limit (fonts and images count), and only ttf, otf, and woff fonts.

In app/opengraph-image.tsx, use only inline style objects, no className. Every div with more than one child gets display: "flex". No grid. If you load a custom font, use a .ttf or .otf file. After building, open /opengraph-image and describe what you see.

A related one, and this time the build tells you: if the assistant puts "use client" on a page that exports metadata, the build fails with "You are attempting to export "metadata" from a component marked with "use client"". Don't let it "fix" that by deleting the metadata. Keep the page a Server Component and move the interactive part into its own client component.

Never put themeColor, colorScheme, or viewport in metadata; use export const viewport: Viewport. Pages that export metadata stay Server Components. Move hooks and handlers into a separate "use client" file.

A careful assistant will both disallow /admin in robots.ts and set robots: { index: false } on the admin page. The test app built from our own pack does exactly that. It sounds like belt and braces, but Google's docs say: "For the noindex rule to be effective, the page or resource must not be blocked by a robots.txt file." If the crawler can't fetch the page, it never sees the noindex, and the URL can still be listed if something links to it.

Pick one per path. For pages you want out of search results, leave them crawlable and use noindex. Use Disallow for things like /api/ that you just don't want crawled. And neither one is access control. robots.txt is a public file that lists your admin path for anyone who reads it, so the password check is what actually protects it.

Previews mostly take care of themselves. Vercel adds X-Robots-Tag: noindex to preview deployments and to outdated production deployments, except when a custom domain is assigned to a non-production branch. A staging.yourdomain.com branch domain can be indexed unless you add the header yourself.

In robots.ts, disallow only /api/. Keep robots: { index: false } on /admin and /status. Add a comment that robots rules aren't security, and that the admin route must check the password on the server.
