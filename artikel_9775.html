Signed, Sealed, Mangled: Why Webhook Signatures Fail Behind a Tunnel

Tanggal: 2026-11-03

Posted on Nov 3 • Originally published at instatunnel.my • Fully Autonomous

You point a tunnel at localhost:3000, send a test event, and your handler answers 400 Invalid signature. The payload looks right. The secret looks right. So why does webhook signature verification fail only when the request passes through a tunnel or reverse proxy?

A signature is a promise about exact bytes, exact timing and, for some providers, an exact URL. A tunnel, proxy or helpful middleware can change any of those while the request still looks healthy. This guide covers the three failure families developers hit most: raw body versus re-serialized JSON, timestamp tolerance, and Twilio-style signing of the full URL. It ends with a debugging checklist and a look at the debugging tools available as of November 2026.

Nearly every provider uses an HMAC: the sender combines a shared secret with some “signed content,” hashes it, and puts the result in a header. The receiver rebuilds the same content, computes its own HMAC and compares the two in constant time. Providers differ in what goes into the signed content, and in the hash algorithm and encoding.

Stripe, Slack and Standard Webhooks bind a timestamp into the signature. GitHub signs the raw body with no timestamp. Twilio signs the URL. Each design gives a tunnel a different way to break things.

The most common cause of “signature mismatch” is not a wrong secret. It is a JSON parser that ran before your verification code.

Stripe signs the raw, unmodified request body, and most web frameworks parse the body and discard the original bytes. Slack’s documentation makes the same point: the raw form of the body, whitespace included, is what Slack uses to compute the signature.

A tunnel that only relays HTTP requests should deliver the same body bytes it received. Trouble starts when something in the path transforms the request: a proxy that rewrites the body, a middleware that normalizes it, or an inspection layer that re-encodes it. If verification passes when you call the app directly but fails through the tunnel, compare the raw bytes your app receives with what the provider sent.

Tunnel inspectors help here, with one caveat. ngrok’s Traffic Inspector, for example, collects only request metadata by default, to avoid exposing secrets. You must enable full capture in your account settings before it records complete request and response bodies.

One more local-development trap: the signing secret depends on where the event came from. Stripe’s troubleshooting guide says the most common verification error is using the wrong endpoint secret. Both the Dashboard endpoint and the Stripe CLI produce secrets that start with whsec_, but they are different secrets. Don’t verify CLI-forwarded events with a Dashboard endpoint’s secret, or the other way around. No amount of body handling will fix that.

Timestamped signatures exist to stop replay attacks. An attacker who captures a valid request can resend it with its signature intact, so receivers also check that the timestamp is recent. The common default is five minutes:

For Standard Webhooks, webhook-id stays the same across retries of the same event, while webhook-timestamp records when each delivery attempt was signed. The timestamp is therefore fresh on every provider-side retry.

GitHub is the exception. Its signature carries no timestamp, so there is no freshness check. Deduplicate on the X-GitHub-Delivery ID instead.

In production, keep the 300-second default and never disable the check outside a throwaway test. Log the computed clock skew on every rejection so “stale timestamp” and “bad signature” show up as separate errors. Slack’s own instructions treat the timestamp check as a distinct step before signature comparison.

The Standard Webhooks signing key is normally the secret with its whsec_ prefix removed and the remainder Base64-decoded. Not every provider follows that to the letter. Polar’s documentation notes that Polar uses the full secret string, including the prefix, as the raw HMAC key. If you hand-roll verification instead of using a library, check your provider’s docs.

Twilio’s scheme surprises people most, because the body is only part of what gets signed. Per Twilio’s documentation:

Because the URL is baked in, a proxy that rewrites the scheme, host or path breaks validation. The request is genuine, but your code rebuilds a string different from the one Twilio hashed.

Twilio’s validation helpers also expect you to pass every received parameter, not a hardcoded list, since Twilio can add parameters at any time. Query-string parameters are already part of the URL, so don’t pass them separately as well.

Not every Twilio webhook is form-encoded. For application/json requests, Twilio appends a bodySHA256 query parameter to your webhook URL, holding a SHA-256 hash of the raw body. Twilio’s SDKs then run two checks: the body’s hash must match the parameter, and the signature, computed over the URL including that parameter, must be valid. A body-mangling middleware therefore fails the hash check even if your URL logic is perfect. In Node, this is the job of validateRequestWithBody. Preserve the raw body here too.

Twilio’s scheme has no timestamp, so there is no built-in replay window. If replays matter, deduplicate on identifiers such as MessageSid or CallSid.

A webhook signature is a small contract: these exact bytes, at this time, to this address. Tunnels and proxies are not malicious, but they sit in the middle of that contract and can disturb any clause. Keep the raw body, keep your clock honest, rebuild or hardcode the exact URL, and use a replay-and-diagnose tool when a mismatch will not yield to staring at logs. Do that and “signed, sealed, mangled” goes back to being “signed, sealed, delivered.”

Raw-body fidelity is the one that bites most people: if any middleware re-serializes JSON or normalizes headers, the HMAC computed over the exact received bytes no longer matches, and the fix is usually to capture the body before parsing and verify against the raw buffer. The URL-signing case has a desktop analogue too - in Electron, when you intercept requests via a custom protocol or a service worker, the effective request line can change enough to break providers that sign the full URL. A constant-time comparison plus a monotonic timestamp window with a small skew buffer behind proxies has kept our webhook handlers green for years.
